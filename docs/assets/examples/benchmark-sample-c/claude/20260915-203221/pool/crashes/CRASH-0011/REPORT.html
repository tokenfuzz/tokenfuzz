Summary¶

The RCF decoder's ARRAY field allocates a fixed-width row table and fills every cell. A stream of the magic RCF1 followed by a single ARRAY field (type 0x03) whose value declares a large row count and row width overflows the 32-bit size used for allocation while the fill loop uses the full 64-bit product, so the loop writes far past a tiny allocation. In handle_array the allocation size is uint32_t total = rows * width (rcfg.c:113) — a 32-bit multiply that wraps — but the loop bound is (size_t)rows * width (rcfg.c:121), a 64-bit multiply that does not.

Root Cause¶

The allocation size and the loop bound are computed with different widths from the same two caller-controlled u32 fields. rows = read_be32(val) and width = read_be32(val + 4) (rcfg.c:111-112). total = rows * width (rcfg.c:113) is uint32_t, so rows == 0x10000 and width == 0x10000 give total == 0x100000000 mod 2^32 == 0; malloc(total ? total : 1) then allocates just 1 byte (rcfg.c:115). The fill loop for (i = 0; i < (size_t)rows * width; i++) (rcfg.c:121) promotes to 64-bit, so its bound is 0x100000000 and table[i] = 0xFF (rcfg.c:122) writes out of the 1-byte buffer on the second iteration. Any rows/width pair whose 32-bit product is smaller than their 64-bit product (or wraps to 0) produces an undersized buffer with an oversized loop. ASan reports a 1-byte heap WRITE immediately past the allocation.

Data Flow¶

The CLI hands the exact stream bytes to the decoder, which dispatches the ARRAY field to the vulnerable handler.

  • step: main (src/rcfg_cli.c:59) — reads the file and calls rcfg_decode.
  • step: rcfg_decode (src/rcfg.c:247) — matches magic, dispatches type 0x03 with the 8-byte value.
  • step: dispatch (src/rcfg.c:210) — routes RCFG_T_ARRAY to handle_array.
  • step: handle_array (src/rcfg.c:113) — total = rows*width wraps to 0 in uint32_t.
  • step: handle_array (src/rcfg.c:115) — malloc(1) since total==0.
  • step: handle_array (src/rcfg.c:121-122) — loop bound (size_t)rows*width == 2^32 writes 0xFF past the 1-byte buffer.

Impact¶

Any caller supplying a crafted RCF stream (file/bytes boundary) triggers a heap out-of-range write. The write value is fixed (0xFF) but the count is enormous (billions of bytes for the wrap-to-zero case), so in practice the process writes until it walks off mapped memory — a reliable, caller-triggered heap corruption / crash. Trigger is deterministic from input bytes.

Fix Direction¶

Compute the size once in a width that cannot wrap and reject overflow before allocating: use size_t total = (size_t)rows * width and, on 32-bit size_t platforms, check width != 0 && rows > SIZE_MAX / width; bound both the malloc and the loop with that single value. Also enforce a sane maximum against the field length. Widening only the loop or only the malloc leaves the mismatch.

Severity rationale¶

Severity is the CVSS v4.0 score — one industry-standard metric, computed by the vendored FIRST reference scorer. Base metrics come from the primitive and surface, with Attack Vector/Requirements also reflecting the trigger's caller-control facts (a trusted local API/call-sequence reads as AV:L/AT:P). The Threat metric (E) is read locally, not from threat intelligence: it grades how far this audit got toward proving the bug — a reproducer that fires is E:P, an unproven argument is E:U — so a demonstrated bug outranks a written one. FIRST defines E against public exploit availability, which is not what is measured here, and nothing in this run is publicly disclosed. Read E as reproduction confidence. The Environmental Security Requirements (CR/IR/AR) are left Not Defined — they model a deploying organisation's asset importance, which the scorer cannot derive, so a generic score keeps the CVSS-B worst case. Environmental modified impacts are set only to floor impact where reachability facts justify it (non-shipping surfaces, caller-only triggers). Cluster size remains a priority/verification fact because CVSS v4.0 has no cluster metric.

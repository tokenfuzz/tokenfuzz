Summary¶

The RCF decoder can stage a heap record, discard it, and later commit it, but the discard handler frees the record without clearing the pointer to it, so the commit handler reads through the freed pointer. A 4-byte magic ("RCF1") followed by a stage field (type 0x05), a drop field (type 0x06), and a flush field (type 0x07) reaches it. The external party gets a 1-byte read of freed heap whose contents they can influence by reclaiming the freed 4-byte region. Mechanism: handle_drop (src/rcfg.c:169) does free(ctx->pending) but leaves ctx->pending non-NULL, and handle_flush (src/rcfg.c:176) then dereferences it as ctx->pending->tag.

Root Cause¶

handle_flush assumes that a non-NULL ctx->pending still points at a live record, but nothing enforces that invariant once a record has been dropped. The context holds rcfg_record *pending (src/rcfg.c:34). handle_stage allocates a record and stores it in ctx->pending (src/rcfg.c:155,163). handle_drop is the whole body free(ctx->pending); (src/rcfg.c:169) — it releases the record but never sets ctx->pending = NULL, leaving a dangling non-NULL pointer. handle_flush guards only on nullness: if (ctx->pending != NULL) ctx->last_tag = ctx->pending->tag; (src/rcfg.c:175-176). Because the drop left the pointer non-NULL, that guard passes and the handler reads ->tag out of the freed 4-byte allocation. The wrong assumption in words: flush treats "pointer is non-NULL" as "record is live", but drop relinquishes the allocation without relinquishing the pointer. This is the read-side manifestation of the same missing pending = NULL that also yields a double-free; here the field ordering stage→drop→flush surfaces it as a use-after-free read at a distinct site (handle_flush) rather than at the end-of-stream cleanup free.

Data Flow¶

The CLI reads the file into a heap buffer and calls the decoder, which stages a record, frees it on drop, then reads through the dangling pointer on flush.

  • read: read_file (src/rcfg_cli.c:34) — reads the whole input file into a heap buffer sized to the file length.
  • entry: rcfg_decode (src/rcfg.c:247) — validates magic and loops over TLV fields, dispatching each by type.
  • stage: handle_stage (src/rcfg.c:155,163) — mallocs a 4-byte record and stores it in ctx->pending.
  • drop: handle_drop (src/rcfg.c:169) — free(ctx->pending) releases the record but leaves ctx->pending dangling (non-NULL).
  • flush: handle_flush (src/rcfg.c:176) — passes the ctx->pending != NULL guard and reads ctx->pending->tag from freed memory.

Impact¶

Any consumer that decodes an untrusted RCF stream (the shipped rcfg CLI decodes a file argument) can be made to read a freed heap object during commit. With control of intervening allocations the freed 4-byte region can be reclaimed with attacker bytes, so the committed ctx->last_tag becomes a value read out of reused heap — an information/state-integrity primitive on top of a reliable crash (denial of service). Exposure is every caller that decodes untrusted RCF input.

Fix Direction¶

Set ctx->pending = NULL immediately after the free in handle_drop. Nulling the pointer makes the flush read, a later stage's free, and the end-of-stream cleanup free all safe. Merely null-checking harder in handle_flush is insufficient because the same dangling pointer also drives a double-free elsewhere; the single owner-nulling fix closes both.

Severity rationale¶

Severity is the CVSS v4.0 score — one industry-standard metric, computed by the vendored FIRST reference scorer. Base metrics come from the primitive and surface, with Attack Vector/Requirements also reflecting the trigger's caller-control facts (a trusted local API/call-sequence reads as AV:L/AT:P). The Threat metric (E) is read locally, not from threat intelligence: it grades how far this audit got toward proving the bug — a reproducer that fires is E:P, an unproven argument is E:U — so a demonstrated bug outranks a written one. FIRST defines E against public exploit availability, which is not what is measured here, and nothing in this run is publicly disclosed. Read E as reproduction confidence. The Environmental Security Requirements (CR/IR/AR) are left Not Defined — they model a deploying organisation's asset importance, which the scorer cannot derive, so a generic score keeps the CVSS-B worst case. Environmental modified impacts are set only to floor impact where reachability facts justify it (non-shipping surfaces, caller-only triggers). Cluster size remains a priority/verification fact because CVSS v4.0 has no cluster metric.

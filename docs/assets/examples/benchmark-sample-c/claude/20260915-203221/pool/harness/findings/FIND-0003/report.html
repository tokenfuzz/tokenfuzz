Summary¶

The RCF decoder retains a CHECK field into a fixed 32-byte buffer inside the decode context so it can be verified when the stream ends. The only bound on the copy length is a debug assert, which the C standard removes when NDEBUG is defined. A stream of RCF1 + one CHECK field (type 0x09) whose declared length exceeds 32 makes the decoder copy up to 65535 caller-supplied bytes into the 32-byte buffer. In the audit's assertions-enabled build the copy is stopped by the assert (SIGABRT, shown in sanitizer-debug-assert.txt); in any release build compiled with -DNDEBUG — which the project's own build guidance and standard release practice mandate — the assert is gone and the copy overruns the context on the decode stack frame.

Root Cause¶

handle_check copies the field value into ctx->check, a uint8_t check[RCFG_CHECK_CAP] with RCFG_CHECK_CAP == 32 (rcfg.c:22, 41), a member of rcfg_ctx that rcfg_decode allocates on its stack (rcfg.c:228). The only length check is assert(len <= sizeof(ctx->check)) (rcfg.c:197), immediately followed by memcpy(ctx->check, val, len) (rcfg.c:198). assert is a compile-time-removable macro: with -DNDEBUG it expands to nothing, so the memcpy runs with no bound at all. len is the field length read from the wire and clamped only to the bytes remaining in the stream (rcfg.c:243-245); a caller sets it to any value in [33, 65535], so the overflow length is caller-chosen. The code treats a debug invariant as if it were an input-validation check, but an assert is not a runtime guard in a shipping build. The comment at rcfg.c:192-194 even states the field "must fit the retained buffer; a longer field ... trips a debug invariant" — confirming the only enforcement is the debug assert.

Data Flow¶

Input bytes flow from the CLI file read into the check handler, whose only length bound is a debug assert removed under NDEBUG.

  • step: rcfg_decode (src/rcfg.c:247) — reads flen from the field header, clamps it to remaining bytes, dispatches type 0x09.

  • step: handle_check (src/rcfg.c:198) — memcpy(ctx->check, val, len) writes up to 65535 bytes into the 32-byte ctx->check, overrunning rcfg_ctx on the decode stack.

Impact¶

In any -DNDEBUG release build, a single CHECK field yields a linear stack write of up to 65535−32 ≈ 65503 fully caller-controlled bytes past a 32-byte buffer, overwriting the remainder of rcfg_ctx (including ctx->pending, a heap pointer subsequently passed to free at rcfg.c:254) and then saved frame state and the return address. This is a classic stack smash with attacker-controlled content and a controllable freed pointer — a strong candidate for control-flow hijack, not merely a crash. Exposure is any service that decodes an untrusted RCF stream in a release build.

Reproducer note¶

check_overflow.bin (RCF1 + CHECK type 0x09, declared length 64, 64 value bytes) drives the path. Against the audit's assertions-enabled ASan build it aborts at the debug assert (sanitizer-debug-assert.txt), proving reachability and that the assert is the sole guard; a build with -DNDEBUG (or -UNDEBUG removed / assert disabled) turns the same input into an out-of-bounds write in handle_check.

Fix Direction¶

Replace the assert at rcfg.c:197 with a real runtime check that either rejects or clamps: if (len > sizeof(ctx->check)) return; (or clamp len to sizeof(ctx->check) before the copy). A debug assert must not be the only bound on a copy whose length comes from untrusted input, because release builds remove it.

Severity rationale¶

Severity is the CVSS v4.0 score — one industry-standard metric, computed by the vendored FIRST reference scorer. Base metrics come from the primitive and surface, with Attack Vector/Requirements also reflecting the trigger's caller-control facts (a trusted local API/call-sequence reads as AV:L/AT:P). The Threat metric (E) is read locally, not from threat intelligence: it grades how far this audit got toward proving the bug — a reproducer that fires is E:P, an unproven argument is E:U — so a demonstrated bug outranks a written one. FIRST defines E against public exploit availability, which is not what is measured here, and nothing in this run is publicly disclosed. Read E as reproduction confidence. The Environmental Security Requirements (CR/IR/AR) are left Not Defined — they model a deploying organisation's asset importance, which the scorer cannot derive, so a generic score keeps the CVSS-B worst case. Environmental modified impacts are set only to floor impact where reachability facts justify it (non-shipping surfaces, caller-only triggers). Cluster size remains a priority/verification fact because CVSS v4.0 has no cluster metric.
